# DSH 多租户多实例管理器 · 调研笔记

> 调研日期：2026-08-22。本文是《02-开发计划》的事实依据。
> 目标形态：部署在一台 Linux 服务器上、多人使用的 DeepSeek Harness（dsh）多实例管理器：
> 网页登录 → 以用户昵称建目录 → 该用户所有实例与数据都收在自己的目录里 →
> 同一用户实例间互相隔离、不同用户之间严格隔离 → 管理员后台统一管理所有用户。

---

## 1. DSH 本体的多实例事实（本机 @deepseek-ai/dsh@0.1.1-rc.2 已验证）

| 事实 | 依据 | 对方案的影响 |
|---|---|---|
| `dsh web` 解析 `--host`、`--port`、可重复 `--trusted-host`、`--no-open` | dsh-web-app README.zh（web-startup 提供方） | 每实例可指定回环地址 + 独立端口 + 来源信任 |
| **拒绝 `--host 0.0.0.0`**（CLI 有意不支持绑全网卡） | 同上 | 实例只能绑 127.0.0.1/内网 IP ⇒ **公网访问必须经反向代理**，这正好逼出"网关统一鉴权"的正确架构 |
| 浏览器侧没有内置账号鉴权，只有基于来源的"浏览器信任栅栏"（LAN 信任信息 + trustedHosts） | dsh-web-app README.zh | **必须由管理器的网关承担登录态校验**，否则任何知道端口的人都能用别人的实例 |
| `$DSH_HOME` 决定全部数据根：`profiles/`、`sessions/`、`storages/`、`settings.yaml`、`.credentials.yaml`(600) | 本机 `~/.dsh` 实测 + dsh-home-paths 包 | 注入不同 `DSH_HOME` 即得到完全隔离的实例数据 |
| 运行命令时所在目录成为默认 workspace 根 | dsh README.zh | 以用户实例自己的 workspace 目录为 cwd 拉起即可 |
| `profiles/web` 首次使用从随包模板自动初始化（initProfile），空目录可直接拉起 | dsh README.zh | 新建实例无需手工初始化步骤 |
| 会话目录名把路径编码进名字（如 `--home-<用户名>-...`） | 本机 `~/.dsh/sessions` 实测 | 不同 HOME 天然不会串会话 |

结论：**DshController 已验证的"实例 = 独立 DSH_HOME + 端口 + workspace"模型可以直接搬到 Linux 服务端**，
缺的只是"多用户 + 鉴权网关 + 管理员后台"这一整层。

## 2. DshController（本地参考项目）可复用经验

来自 `杂项/DshController/源码`：

- **InstanceDef 模型**：home/port/trustedHosts/workspace/harnessVersion 字段划分 —— 直接沿用并加 ownerId；
- **PortAllocator**：约定端口段（3080–3099）、先查配置再真实探测 —— 服务端改为 DB 记账 + 探测双保险，段扩大到 3080–3999；
- **实例锁**：`<home>/.dsh-instance.lock` 记 PID，防止同一 HOME 被重复拉起 —— 保留，另加 DB 层状态；
- **就绪探测**：TCP 握手轮询（不依赖 HTTP 语义），最长等待窗口 —— 服务端同款；
- **停止**：进程组 TERM→KILL 升级 + 端口释放确认 + pidfile 校验防 PID 复用误杀 —— Linux 下用 `setsid` 进程组 + `kill(-pgid)` 实现；
- **harness 版本固定**：`npx --yes @deepseek-ai/dsh@<版本>`，免全局安装 —— 多用户服务器强烈建议保留（管理员锁定白名单）；
- **凭据模板复制**：WSL 实例首启时把模板 credentials 复制过去并 `chmod 600` —— 正好是"管理员给新用户实例预置凭据"的原型；
- **错误报告文化**：失败生成 Markdown 诊断报告 —— 服务端做轻量版：启动失败快照落盘到实例 `logs/` 并在 UI 展示。

## 3. GitHub 可借鉴项目盘点

### 3.1 QuantumNous/new-api —— 登录与角色体系（主要抄这里）

- Go(Gin)+React。**会话用 Gin session cookie（HttpOnly）**，另有 access_token 供 API 调用；
- **用户角色三级：普通用户 / 管理员 / root**；**第一个注册的用户自动获得管理员身份**（社区讨论确认）；
- 注册开关可配置（开放注册 / 关闭仅管理员建号），支持邮箱验证、Turnstile、OAuth/OIDC、2FA；
- 管理后台：用户列表、搜索、启用/禁用、重置密码、分组额度管理。
- **借鉴**：首用户=root、注册开关、角色三级、session cookie + 个人 API token 双通道、管理员的用户管理页结构。

### 3.2 Wei-Shaw/sub2api —— 首启向导 + 双令牌（次要借鉴）

- **首次启动 setup 向导创建管理员**（默认生成管理员邮箱/密码，环境变量可覆盖）；
- JWT access + refresh 双令牌；admin API 可为普通用户预配 API key；长期凭据走 API key 而非短效 JWT（issue #2843/#466 的演进方向）。
- **借鉴**："首启向导"体验比"首用户自动 root"更可控，两者取其一；给自动化脚本发长效 token、给人发短效会话的双轨制值得抄。

### 3.3 jupyterhub/jupyterhub —— 多用户单机服务的经典三件套

- 架构 = **Authenticator（登录）→ Hub（控制面/数据库）→ Spawner（为每个用户拉起单用户服务器）→ 可配置 HTTP 代理（按 URL 把请求路由到对应单用户服务器）**；
- 单机发行版 The Littlest JupyterHub（TLJH）证明"一台 Linux 机器服务多人"完全可行；
- 教训：单用户服务器要支持 **URL 前缀（base_url）** 才能挂在 `/user/<name>/` 路径下 —— 应用不改造就只能靠子域名。
- **借鉴**：控制面/数据面分离、代理路由独立成模块、"每用户一个常驻服务进程"的生命周期管理范式。

### 3.4 viperproject/code-server-hub —— 形态最接近的小型参考实现

- 多用户 code-server 中枢：nginx 反代 + 为每个用户 spawn 独立 code-server 进程 + 用户管理；规模小、易通读，当"最小可行参照"。

### 3.5 pterodactyl/panel + wings —— 管理面板范式

- 角色 / 资源所有权 / 资源限额（CPU、内存、磁盘）/ 审计动作的设计非常成熟；隔离靠 Docker（每服务器一容器）。
- **借鉴**：管理员↔用户↔实例三层权限模型、配额字段设计、审计日志粒度。容器隔离可作为远期可选强化（见 §5 L5）。

### 3.6 其他

- coder/code-server 文档：反代（子域名/子路径）+ WebSocket 升级的注意事项；
- oauth2-proxy / Authelia / Authentik：后期接企业 SSO 的现成 IdP/前置代理，本期不做接口预留。

## 4. 关键技术决策的对比研究

### 4.1 浏览器如何访问到"我的实例"？——三种路由模式

| 模式 | 做法 | 优点 | 缺点/风险 | 结论 |
|---|---|---|---|---|
| A. 子域名 | `https://<用户slug>-<实例>.dsh.example.com` → 网关按 Host 转发到 127.0.0.1:port | 无路径改写问题；与 dsh 按来源的信任栅栏天然契合 | 需泛解析 DNS + 泛域名 TLS；`--trusted-host` 要逐实例传对应子域 | **首选** |
| B. 路径前缀 | `https://gw/u/<用户>/i/<实例>/` | 不需要 DNS/证书配合 | dsh 前端是按根路径构建的 Vite SPA，绝对路径资源大概率 404；未验证 base_path 支持 | 弃（除非 spike 证明可行） |
| C. 每实例公网端口 | 网关为每个实例开公网监听端口，校验会话后转发 | 零 DNS 要求 | 端口暴露面大、防火墙难管 | **备选兜底**（无泛解析的环境用） |

A/C 共享同一套"会话校验 + 所有权校验 + HTTP/WebSocket 转发"核心，只是路由键不同（Host vs 端口）。

### 4.2 用户间"严格隔离"做到哪一层？

| 层级 | 方案 | 成本 | 采用 |
|---|---|---|---|
| L1 目录隔离 | 每用户根目录 chmod 700 + 专用系统账号跑管理器与实例 | 低 | **必做（基线）** |
| L2 进程标签 | 每实例独立进程组/会话（setsid），pidfile 防串 | 低 | 必做 |
| L3 资源限额 | systemd-run --scope 按实例设 MemoryMax/CPUQuota/PidsLimit | 中 | M5 |
| L4 OS 用户隔离 | 每平台用户一个 Unix 账号，其实例进程 setuid 后运行（内核级文件权限隔离） | 高 | **可选硬隔离档**（"严格模式"开关） |
| L5 容器隔离 | 每实例一容器（rootless podman/Docker），Pterodactyl 式 | 很高 | 远期，不进本期 |

### 4.3 控制面技术栈

- **Node.js 24 + TypeScript**：与 dsh 同运行时，spawn/env 注入（DSH_HOME）零成本，可直接复刻 DshController 的生命周期状态机；
- Web 框架 Fastify；控制面数据库 **SQLite(WAL)**（单机免运维、事务够用）；前端 React+Vite，复用 DSH 设计令牌（品牌蓝 #3964FE 等）保持观感一致；
- 代理：自研薄网关（undici/http-proxy + WS upgrade），外面套 Caddy 做 TLS 与泛域名证书（生产拓扑），内网/测试可裸跑明文网关。

## 5. 待技术验证清单（Spike，进 M0/M1）

1. **S1 代理可达性**：dsh web 绑 127.0.0.1，经 Node 反代（含 WebSocket upgrade）全功能可用；确认引导流程在代理后正常；
2. **S2 trusted-host 匹配规则**：`--trusted-host` 是否接受通配/后缀（如 `.dsh.example.com`），决定逐实例传完整子域还是可共享配置；
3. **S3 systemd-run 限额**：非特权服务账号能否 `systemd-run --scope --uid=` 给实例设 MemoryMax/CPUQuota；
4. **S4 npx 版本固定**：无全局 dsh 的干净环境下 `npx @deepseek-ai/dsh@<ver>` 冷启动耗时与缓存行为；
5. **S5 昵称目录**：中文昵称作目录名在 ext4 的实际表现（UTF-8 字节、备份工具兼容性），确定净化规则。
